Business capabilities don't map directly to technical capabilities — there's typically an intermediary layer, and treating it as a direct link is a common architecture mistake.
The standard chain looks like this: business capability → application/system (or application capability) → technology capability (infrastructure, platforms, technical services). The application layer is the bridge. A business capability like "Order Management" is realized by one or more applications (an OMS, an ERP module, a custom system), and those applications in turn depend on underlying technical capabilities (compute, data storage, integration/middleware, security services). So the mapping most architects actually maintain is a capability-to-application map, not a capability-to-technology map.
There are a few reasons this indirection matters rather than being pedantic. First, cardinality is messy in both directions — one business capability is often supported by multiple applications (legacy plus new), and one application often supports multiple capabilities, which is exactly the kind of overlap you're trying to surface when you build a capability heat map or rationalize an application portfolio. Second, the application layer is where cost, risk, and technical debt actually live — you assess an application's fit, cost, and health, then roll that assessment up to say "capability X is technically at risk" because the app(s) behind it are aging or unsupported. Third, some frameworks add a further layer between capability and application called a "capability enabler" or "IT capability," particularly in BIZBOK and some TOGAF-derived models, to separate the abstract technical function (e.g., "customer data management") from the concrete system that implements it (a specific CDP or CRM instance) — useful when planning to swap out an application without changing the underlying technical capability it fulfills.
A rough way to picture the stack: Business Capability → enabled by → Application(s) → running on/using → Technology Capabilities/Infrastructure, with data entities and business processes cutting across all three layers (a process consumes a capability; a capability is realized by an application; an application manages data). Most capability-to-application matrices in practice (including the kind used in your APM data model earlier in this conversation) are built exactly on this middle link, since that's the layer that's actually inventoried, costed, and governed.
Application capabilities describe what a specific application or system can do — the functional abilities it exposes, independent of the underlying infrastructure. "Process a payment," "generate a picking list," "apply a loyalty discount," "reserve inventory," or "send a transactional email" are application capabilities: they're scoped to a piece of software and framed in terms a business person could still recognize, even though they're one level more granular and system-specific than a business capability like "Order Fulfillment."
Technical capabilities sit a layer below and are infrastructure/platform-oriented rather than software-function-oriented. They describe the underlying technical services that any application draws on to actually run: things like compute provisioning, data storage and retrieval, message queuing/integration, identity and access management, load balancing, caching, logging/monitoring, encryption, API gateway services. A technical capability doesn't know or care what business problem it's serving — "distributed caching" is the same technical capability whether it's speeding up a checkout page or a warehouse dashboard.
The cleanest way to see the difference: application capabilities answer "what can this system do for the business," while technical capabilities answer "what does this system need from the platform to work." An application capability like "check real-time inventory availability" is realized using technical capabilities like a database query service, a caching layer, and an API integration service. If you swapped out the underlying tech stack (say, migrated the database or moved from on-prem to cloud), the application capability wouldn't change — the business-facing function is identical — but the technical capabilities supporting it would be completely different.
This is also why the two are governed differently in practice. Application capabilities usually live in an application capability matrix mapped up to business capabilities (feeding your capability-to-application heat maps), while technical capabilities live in a technology reference model or infrastructure capability map, often owned by a separate infrastructure/platform architecture team rather than the business architecture or application architecture team. A capability-to-application-to-technology traceability chain, when done well, lets you answer both "which business capabilities are at risk if this application is retired" and "which business capabilities are at risk if this database platform goes end-of-life," which are genuinely different questions that require different layers of the model.
