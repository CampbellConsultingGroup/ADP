# Research: C4 Design View

## Decision 1: Container/boundary grouping is descoped, not built (reflected in spec.md FR-004)

**Decision**: This feature does not add any way to persist a labeled grouping of elements
("boundary" in C4 terms). The reused canvas's own "Add Container"/"Group into Container" toolbar
controls remain visually present (a byproduct of reusing the shared, unmodified `Canvas.tsx`), but
any grouping a user creates has no effect on saved data — it exists only within the current
editing session.

**Rationale**: Confirmed directly by reading `web/src/canvas/C4Canvas.tsx` in full — the screen
this feature replaces has **no** grouping/boundary capability today (`ADD_ELEMENT_KINDS` covers
only `person|system|container|component`, all *element kinds*, not a separate grouping concept).
Confirmed further by reading `src/adp/models.py`'s `ArchitectureDescription` field list — there is
no `containers`/`boundaries`/`groupings` field anywhere in the canonical model. Building real,
persisted support would mean adding a genuinely new entity to the platform's governed
architecture-design record (new Pydantic model, new JSONB shape, a schema version bump, new
referential-integrity rules in `validate.py`) — exactly the kind of deliberate, ART-XV-governed
schema decision that deserves its own spec, not to ride along inside a UI-migration feature whose
own spec never asked for new canonical-model concepts. This was caught during planning (not spec
time) because the spec's own FR-004 had implicitly assumed grouping was "reuse an existing
capability" by extrapolating from the *reused canvas component's* toolbar, without checking
whether the screen actually being replaced ever had it. spec.md's US1, FR-004, Edge Cases, Key
Entities, and Assumptions were all corrected in this same pass (ART-I: a behavior change is
reflected in its spec) rather than silently building something spec.md didn't actually describe.

**Alternatives considered**:
- *Add a new `ContainerGrouping` entity to the canonical model now* — rejected: real, non-trivial
  schema work (new model, schema version bump, new referential-integrity rules) that deserves its
  own deliberate spec and its own constitution-check pass, not to be an implicit side effect of a
  migration feature.
- *Hide the "Add Container"/"Group into Container" buttons for this screen* — rejected: `Canvas.tsx`
  is vendored and its toolbar isn't gated per-`dslFamily` for these two controls (only "Auto
  Layout" is, and only for the `flowchart` family) — suppressing them would mean either modifying
  the vendored component (against the established convention) or a fragile CSS-hiding hack keyed
  to DOM structure. Leaving them visible-but-non-persisting, clearly documented, is more honest
  than either.

## Decision 2: Element/relationship IDs generated by max-plus-one, not count-plus-one

**Decision**: New element/relationship IDs (`ELM-NNN`/`REL-NNN`, per `models.py`'s
`Field(pattern=r"^ELM-\d{3}$")`) are generated as `max(existing numeric suffixes, default=0) + 1`,
not `len(existing) + 1`.

**Rationale**: The existing precedent (`src/adp/recommendation/orchestrator.py:226`,
`elm_id = f"ELM-{len(design.elements) + len(created_elements) + 1:03d}"`) is safe *only* because
that code path never deletes elements — IDs are always contiguous when only additions happen. This
feature is the first to add element/relationship **deletion**, which can create ID gaps (e.g.
`ELM-001`, `ELM-003` after `ELM-002` is deleted) — under the existing `len+1` formula, a
subsequent add would generate `ELM-003` again, colliding with the surviving element and raising
`build_id_index`'s "Duplicate entity IDs detected" error on save. `max+1` is collision-safe
regardless of gaps.

**Alternatives considered**:
- *Keep the existing `len+1` pattern for consistency* — rejected: it's not actually safe once
  deletion exists, and "consistent with a pattern that has a latent bug in the exact scenario this
  feature introduces" is not a real virtue.

## Decision 3: Layout "migration" (FR-013) is continued reuse of an existing endpoint, not a data migration

**Decision**: The new view calls the *same, unmodified* `GET /designs/{id}/layout/{level}` /
`PUT /designs/{id}/layout/{level}` endpoints (`src/adp/api/routers/layouts.py`) C4Canvas already
calls today, via the same debounced-save pattern C4Canvas already uses. No backend change, no
migration script, no new storage.

**Rationale**: Confirmed directly by reading `layouts.py` in full: `design_layouts` is not a
database table at all — it's an **in-process Python dict** (`_layout_store: dict[tuple[str, str],
...] = {}`), explicitly documented in the file's own header comment as "v1: in-process dict
(transient). A process restart clears positions." There is nothing to migrate *from* in the
data-migration sense — there's no persistent store with data to carry forward, only a live
endpoint that may or may not currently hold positions in whatever process is running. FR-013's
actual, correct behavior is simply: the new view reads from this endpoint on load exactly as
C4Canvas already does, so whatever's there (if anything) is used, and whatever isn't falls back to
auto-layout — identical behavior to today, just from a new caller. The endpoint's real persistence
characteristics (or current lack thereof) are unrelated to and unaffected by this feature.

**Alternatives considered**:
- *Build a real migration path assuming `design_layouts` is a persisted table* — rejected: would
  have designed for storage that doesn't exist, based on the source bead's own (reasonable, but
  incorrect) assumption. Worth flagging directly.
- *Move position storage into the C4 DSL's own front-matter now (as the diagram tool already does
  for standalone diagrams)* — considered as a real future improvement (this feature's canvas
  positions would then actually persist across restarts, closing a pre-existing gap C4Canvas has
  always had) but rejected for *this* feature: it would mean routing position writes through the
  adapter's DSL round-trip rather than the existing layout endpoints, a materially bigger change
  than "reuse what's there," and isn't required by any FR. Worth filing as a future enhancement.

## Decision 4: Element inspection/technology-tag editing is driven by an explicit picker, not canvas click-selection

**Decision**: The new view's element-detail affordance (technology metadata viewing/editing,
FR-008) is reached via an explicit, ADP-authored list/picker of the design's elements — not by
clicking a node on the canvas. `InspectionPanel.tsx`/`TechnologyEditor.tsx` are reused completely
unchanged for the actual detail rendering; only how they're *triggered* differs from C4Canvas.

**Rationale**: Confirmed directly: `Canvas.tsx`'s `CanvasProps` exposes no selection-change
callback (`model`, `onChange`, `dslFamily`, `toolbarContainer` — full stop); its `selectedIds`/
`selectedContainerId`/`selectedEdgeId` are private internal state with no way for a parent
component to observe them. C4Canvas's own click-to-inspect flow depends entirely on ReactFlow's
own node-click callback, which has no equivalent being exposed here. Adding a new callback prop to
`Canvas.tsx` to support this would be a real, structural change to a vendored file — a materially
bigger exception than the two narrowly-scoped, one-line *value* exceptions ADP-SPEC-052 already
established as the acceptable boundary. `InspectionPanel.tsx` itself (confirmed by reading it in
full) has zero coupling to ReactFlow or `useWorkspaceStore` internally — it's a plain
`{elementId, design, onClose}` component, trivially reusable once *something* supplies those
props. An explicit picker is that something, at the cost of "click the node to inspect it" not
being available in this feature's first cut.

**Alternatives considered**:
- *Add an `onSelectionChange` callback to `Canvas.tsx`* — rejected: the vendoring convention this
  session has consistently maintained (ADP-SPEC-052/053) draws the line at value-only, one-line
  exceptions; a new prop is a structural API change, a different category of exception entirely.
- *Poll the DOM for `data-testid="node-{id}"` selection state via a `MutationObserver`* —
  rejected: fragile, couples to incidental DOM structure rather than a real API, and harder to
  test than an explicit picker.

## Decision 5: Canvas edits commit immediately per action, via a reconciliation layer — not staged-and-saved

**Decision**: Unlike the standalone diagram tool's flow (stage edits locally in a `DiagramModel`,
persist the whole `dsl_source` string on an explicit Save click — ADP-SPEC-046/052/053), this
feature's canvas interactions commit **immediately**, one backend call per user action (add one
element, delete one relationship, etc.) — matching C4Canvas's own existing behavior
(`usePlaceElement`/`useDrawRelationship` already fire on each toolbar action, not behind a Save
button). A new reconciliation function diffs each `Canvas.tsx` `onChange(model)` callback against
the previously-known model to determine exactly what changed, then calls the one specific granular
endpoint that matches.

**Rationale**: `Canvas.tsx` (vendored, unchanged) only exposes a single `onChange(wholeModel)`
callback — there is no finer-grained "this one node was added" signal available without modifying
it (same boundary as Decision 4). The reconciliation layer is therefore necessary glue, not
optional polish: it's what makes "commit per action" possible on top of a component that only
speaks "here's the whole model now." It also owns id reconciliation — `Canvas.tsx` generates its
own temporary node/edge ids when a user adds a shape; once the backend returns the real
`ELM-NNN`/`REL-NNN` id, the reconciler updates the controlled `model` state to replace the
temporary id with the real one (a normal controlled-component update, the same mechanism
`DiagramEditorPage.tsx` already uses when `applyDsl` replaces the whole model on load).

**Alternatives considered**:
- *Stage edits locally and require an explicit Save, matching the standalone diagram tool's UX* —
  rejected: this would reintroduce the exact whole-design-overwrite race condition this feature
  exists to eliminate (the granular-endpoints requirement, bead-flagged sub-decision #2), and
  diverges from C4Canvas's own already-established "actions commit immediately" UX architects
  already expect from this specific screen.

## Decision 6: Canonical `ElementKind` stays at its current 4 values — no Db/Queue/`_Ext` sub-kinds added

**Decision**: The adapter maps `Element.kind` (`person|system|container|component`) directly onto
`DiagramNode.role` — an exact string match, confirmed by reading both `models.py`'s `ElementKind`
`StrEnum` and `core/dsl/c4.ts`'s `ELEMENT_TO_ROLE` table, no translation table needed. When a
`DiagramModel` produced by editing DSL text directly uses a database/queue/external C4 sub-kind
(`SystemDb`, `ContainerQueue`, `Person_Ext`, etc. — all fully supported by `c4.ts`'s parser), the
adapter's save-back-to-canonical-Elements step **does not** attempt to preserve that distinction —
it maps to the plain base kind (`SystemDb` → `Element.kind = "system"`), since the canonical model
literally has no field to hold it (`models.py`'s own comment: `"C4 structural element types. Stops
at component level (v1 scope)."`).

**Rationale**: The C4 DSL format is, in this one respect, strictly more expressive than the
canonical model it's being used to edit. Expanding `ElementKind` to add sub-kind/external markers
is the same category of decision as Decision 1 (a deliberate, governed schema change) and is
similarly out of scope for a feature about *replacing an editing surface*, not *expanding what the
canonical model can express*. This narrowing only affects the advanced case of directly typing DSL
text with Db/Queue/`_Ext` keywords (US1's primary flow — toolbar-driven element creation — never
produces these in the first place, since the toolbar only offers the four base `ElementKind`
shapes).

**Alternatives considered**: None seriously — adding new `ElementKind` values is real schema
scope creep for the same reasons as Decision 1, not a genuine two-sided tradeoff.

## Decision 7: No optimistic-concurrency (`expected_version`) adoption in this feature

**Decision**: New endpoints call `store.save(design, actor=actor)` without `expected_version` —
identical to how every existing design-mutation endpoint already calls it (`tags.py`, `layouts.py`,
`intake/orchestrator.py`, `recommendation/orchestrator.py` — confirmed via direct grep, zero
existing callers pass `expected_version`).

**Rationale**: `DesignStore.save()` already implements real optimistic-concurrency support
(`expected_version` parameter, raises `ConcurrencyConflictError` on mismatch) — but confirmed,
directly, that no endpoint in the entire codebase actually uses it today. Being the first to adopt
it would mean this feature invents new conflict-handling semantics (what HTTP status, what retry
UX, what the frontend does on a 409) that spec.md's own Assumptions explicitly deferred
("Explicit real-time conflict notification... is out of scope for this feature"). Matching the
existing, universal precedent keeps this already-large feature's scope bounded; adopting
`expected_version` platform-wide (starting here or elsewhere) is a reasonable, independently-valuable
future improvement, not a requirement this feature's own spec makes.

**Alternatives considered**:
- *Be the first endpoint to use `expected_version`* — rejected for this feature specifically: real
  value, but a genuinely separate decision (touches UX, not just backend plumbing) that spec.md's
  own Assumptions already scoped out.

## Decision 8: Reached via a new, separate entry point — not a swap of the existing "Canvas" nav item

**Decision**: This feature adds a new, distinct way to reach the C4 Design View (a new route/nav
affordance), while the existing "Canvas" nav item continues to open the legacy `C4Canvas.tsx`
screen unchanged, for the duration of this feature.

**Rationale**: Matches the already-approved roadmap's own phase boundaries precisely — `ADP-914.13`
(the next bead in this same roadmap, already filed) explicitly owns "Remove the 'Canvas' nav item"
and "Repoint `RecommendationPage.tsx`'s post-accept redirect," gated on this feature "landing and
demonstrably covering C4Canvas's real feature set first." If this feature performed the nav swap
itself, `ADP-914.13` would have nothing left to do beyond a file deletion, contradicting the
phased structure already decided on `ADP-914.9` and reflected in both beads' own descriptions.

**Alternatives considered**: None — this is a direct consequence of a sequencing decision already
made and recorded on the roadmap's own beads, not a fresh tradeoff to weigh here.

## Decision 9: Export requires zero backend change — both endpoints already exist and already satisfy FR-009/FR-010

**Decision**: The new view's Export actions call `POST /api/v1/designs/{id}/render`
(`src/adp/api/routers/render.py`) and `GET /api/v1/designs/{id}/export/calm`
(`src/adp/api/routers/calm.py`) directly — the exact same endpoints `Workspace.tsx`'s
`handleExportCalm` and the render pipeline already call today. No new endpoint, no new export
logic.

**Rationale**: Confirmed by reading both router files directly: `render.py`'s
`RenderRequest`/`RenderResult` already apply the locked theme exclusively (`ART-XII / FR-002:
RenderRequest.extra="forbid" — no style override fields accepted`, per the file's own docstring) —
exactly FR-009's requirement, already met, already correct. `calm.py`'s existing CALM export
endpoint already produces the shape FR-010 requires. The only genuinely new frontend work is
wiring an Export action in the new view's UI to these pre-existing endpoints (mirroring
`Workspace.tsx`'s own existing `handleExportCalm` implementation) — not building anything new
server-side.

**Alternatives considered**:
- *Reuse the standalone diagram tool's own `ExportAction.tsx` client-side export path instead* —
  rejected outright, and already the subject of an explicit governance constraint carried forward
  from ADP-SPEC-052/053's own research: that path renders via a generic, unstyled client-side
  renderer, not the ART-XII-governed locked theme — using it here would silently violate FR-009.
