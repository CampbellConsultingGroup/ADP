# Implementation Plan: Application Registry

**Branch**: `036-application-registry` | **Date**: 2026-07-11 | **Spec**: [spec.md](spec.md)

## Summary

Add a first-class `Application` entity to ADP and wire it to all existing business architecture dimensions (business capabilities, technical capabilities, value stream stages, business domains) plus point-to-point integration topology and design traceability. A new `adp.application` module (models.py, store.py, router.py) is created, parallel to `adp.business`. Eight new tables land in Alembic migration 010. The frontend gains an "Applications" nav section with CRUD views for applications, a technical capability tree manager, and an integration registry.

## Technical Context

**Language/Version**: Python 3.12 (backend); TypeScript 5.x (frontend)
**Primary Dependencies**: FastAPI ≥ 0.111, SQLAlchemy 2 async (Core), asyncpg, Pydantic v2, React 18, TanStack Query v5 — all existing stack; zero new packages
**Storage**: PostgreSQL 16; Alembic migration 010 (`down_revision = "009"`): 8 new tables
**Testing**: pytest (unit + integration), Vitest (frontend unit)
**Target Platform**: Linux server + browser
**Project Type**: web-service (backend) + web-application (frontend)
**Performance Goals**: All new endpoints < 500 ms p99 at single-user load; integration list query < 200 ms for portfolios up to 500 applications
**Constraints**: Zero new packages; new `adp.application` module; existing business router untouched; SA Core only (no ORM mapper)
**Scale/Scope**: Small-to-medium data volumes — typically < 500 applications, < 100 technical capabilities, < 1000 integrations

## Implementation Phases

### Phase 1: Setup — Migration + Module Init

**Migration 010** — `src/adp/store/migrations/versions/010_application_registry.py`

Eight new tables (see data-model.md for full SQL):
1. `applications` — core entity with TIME/R/pace/health fields
2. `technical_capabilities` — self-referential 3-level hierarchy; RESTRICT on parent delete
3. `application_capability_links` — app×business_cap join + fit_score; composite PK; both FK CASCADE
4. `application_tech_cap_links` — app×tech_cap + usage_type; composite PK (all 3 cols); both FK CASCADE
5. `application_stage_links` — app×stage join; composite PK; both FK CASCADE
6. `application_domain_integrations` — app×domain with type + direction; UUID PK; both FK CASCADE
7. `application_integrations` — source×target with type + description; UUID PK; both FK CASCADE; DB CHECK source ≠ target
8. `application_design_links` — app×design join; composite PK; both FK CASCADE

**Module init** — create `src/adp/application/__init__.py` (empty)

**Unit tests** — `tests/unit/application/test_models.py`

Cover every Pydantic model:
- `ApplicationCreate`: blank name → error; invalid TIME/R/pace → error; health_score 0 → error; health_score 6 → error; all valid
- `ApplicationUpdate`: blank name → error; None name → ok (no update)
- `TechnicalCapabilityCreate`: blank name → error; valid with and without parent_id
- `ApplicationCapabilityLinkCreate`: fit_score 0 → error; fit_score 6 → error; fit_score 1–5 → ok
- `ApplicationIntegrationCreate`: source == target → error; valid A≠B → ok; invalid integration_type → error
- `ApplicationDomainIntegrationCreate`: blank integration_type → error; invalid direction → error
