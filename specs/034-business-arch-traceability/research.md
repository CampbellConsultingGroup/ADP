# Research: Business Architecture Traceability (ADP-SPEC-034)

**Feature**: 034-business-arch-traceability
**Generated**: 2026-07-10
**Status**: Complete — all decisions resolved

---

## Decision 1: Module placement for link CRUD

**Decision**: Extend the existing `adp.business` module (new functions in `store.py`, new endpoints in `router.py`) rather than creating a separate `adp.traceability` module.

**Rationale**: The link tables directly reference business entities (`capability_id`, `value_stream_id`) managed by `adp.business`. Keeping link CRUD cohesive with its business entities avoids splitting concerns across two modules for tightly related data. The business router already imports the designs router pattern and can call the design store for lookups.

**Alternatives considered**: A separate `adp.traceability` module. Rejected: adds module overhead, splits logically related code, and the link operations are simple join-table CRUD with no independent domain logic.

---

## Decision 2: CASCADE delete strategy for FK references

**Decision**: Both join tables use `ON DELETE CASCADE` for BOTH foreign keys:
- `capability_design_links.capability_id` → CASCADE (deleting a capability removes all its design links)
- `capability_design_links.design_id` → CASCADE (deleting a design removes its capability links)
- Same pattern for `value_stream_design_links`

**Rationale**: Spec FR-005, FR-006, FR-011, FR-012 all require orphan-free deletion. Database-level CASCADE is safer than application-level cleanup and atomic with the delete transaction. Designs are hard-deleted (no soft-delete in the `designs` table) so orphan links would persist without CASCADE.

**Evidence**: `designs` table has no `deleted_at` or soft-delete column (checked `001_initial_schema.py`). Business entity deletion is already implemented via CASCADE in migration 007 for stages.

**Alternatives considered**: Application-level cleanup in the router (delete links before deleting entity). Rejected: not atomic, complex, races possible.

## Decision 3: ART-IX audit logging approach

**Decision**: Use structured `logger.info()` logging for link mutations (same as ADP-SPEC-033), not writes to the `audit_entries` table.

**Rationale**: The `audit_entries` table uses globally-unique `id` values formatted as `AUD-NNN`, generated by scanning the `design.audit_log` JSONB list (`write_audit_record`). Writing directly to the table would require loading the full `ArchitectureDescription` (to generate the next ID) and re-saving it — creating a new design version solely for a link event. This is architecturally wrong: a link to a capability is not a mutation of the design's architecture description.

A future migration can add a dedicated `business_audit_entries` table (without the `design_version` FK constraint) for business-tier events. ART-IX is SHOULD for this feature (per spec), not MUST; structured logging satisfies the observability principle (ART-VI).

**Justification recorded**: Per spec "ART-IX — traceability link mutations SHOULD be audit-logged so there is a record of when a design was associated with a business capability". The link tables themselves ARE the persistent record; structured logs provide the when/who for operations tooling.

## Decision 4: Design list endpoint for link creation UI

**Decision**: Use the existing `GET /api/v1/designs` endpoint (from the `designs` router) to populate the design picker in the link creation UI. Returns `DesignSummary` objects with `id` and `title`.

**Rationale**: The endpoint already exists, is paginated, and returns exactly the fields needed (id + title). No new backend endpoint required. The frontend will call it with a small `page_size` and search filter.

**Evidence**: `DesignSummary` model in `designs.py` has `id`, `title`, `lifecycle_status`. The `GET /api/v1/designs` endpoint supports `page`, `page_size`, and `status` query params.

---

## Decision 5: Frontend link UI pattern — inline expanded section

**Decision**: Add an expandable "Linked Designs" section to `CapabilityNode.tsx` (toggled by a "Links" button, inline below the node header). For `ValueStreamDetail.tsx`, add a "Supporting Designs" section as a card below the stages list. For design detail (IntakePage), add a `BusinessContextPanel.tsx` component as a sidebar section.

**Rationale**: Avoids introducing a separate "Capability Detail" page which would require new routing and page lifecycle management. Keeps the capability tree compact while still allowing link management. Consistent with how `CapabilityForm` and add-child forms are handled inline in the existing tree.

**Alternatives considered**: Dedicated `CapabilityDetailPage` with full-page navigation. Rejected: requires routing changes, adds navigation complexity, overengineered for the link volume expected (typically <10 designs per capability).

---

## Decision 6: "Business Context" panel placement — IntakePage

**Decision**: Add `BusinessContextPanel.tsx` as a collapsible section in the `IntakePage` sidebar/bottom area, visible when the current design has links. The panel shows which capabilities and value streams the design is linked to, with navigation buttons to the Business page.

**Rationale**: `IntakePage` is the primary per-design landing page (first tab seen after selecting a design). It has a `designId` prop and an `onNavigate` callback already wired. Adding a business context section there satisfies US3 (FR-013–FR-015) without creating a dedicated "design detail" page.

**Alternatives considered**: Adding to `Workspace` (canvas). Rejected: the canvas is a diagram tool; a business context panel there is unexpected. Adding a new "Design Detail" view. Rejected: excessive scope for this feature.

---

## Decision 7: Unique constraint scope

**Decision**: UNIQUE constraint on `(capability_id, design_id)` and `(value_stream_id, design_id)` in the database, plus a 409 Conflict API response on duplicate link attempt.

**Rationale**: Per spec edge case: "the join is unique on (capability_id, design_id)". Database-level enforcement is the safest guarantee. The API should catch the integrity error and return 409 rather than 500.

---

## Decision 8: No new packages

**Decision**: Zero new packages. All implementation uses the existing stack: SQLAlchemy 2 async, FastAPI, Pydantic v2, asyncpg, React 18, TanStack Query v5.

**Rationale**: Join-table CRUD is structurally identical to the existing business entity CRUD (migration 007). No graph, no vector, no LLM — pure relational joins.
